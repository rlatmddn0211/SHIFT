# SHIFT 디자인·협업·시연·검증 계획

기준일: 2026년 11월 13일. [전체 기획안 v1.1](PLAN.md)과 [결정 기록](DECISIONS.md)을 따른다. 아래는 사용자와 정한 제작 기준이며, 화면·앱·계정·실증이 이미 준비되었다는 의미는 아니다.

## 1 출품의 중심

**배정받은 차량 탑승 → SHIFT 인증 → 내 방문 업무 확인 → 목적지 전달 → 방문 후 메모 → 개인 세션 종료.**

사내 차량 관리 앱은 확장으로 남긴다. 회사·차량 등록 관리자 화면, 차량 예약·취소·연장, 대여 승인·차량 반납 처리와 운영 이력은 초기 필수 구현과 1차 시연에서 제외한다. 시험 회사·차량 식별정보는 사전 설정한다.

OneNote 실제 조회·음성 메모 저장과 YouTube Music 실제 이용은 기존에 확정한 범위를 유지한다. 음악은 보조 기능으로 두고, 공식 직접 연동 경로가 확보되지 않으면 휴대폰 공식 앱·차량 오디오 경로를 검증한다.

## 2 디자인 기준

| 항목 | 결정 |
| --- | --- |
| 기존 Figma·로고·스케치·참고 앱 | 없음. 신규 화면 방향으로 시작 |
| 차량 화면 | 짙은 배경의 차분한 업무 도구. 큰 글자·버튼, 짧은 조작과 명확한 상태 표시 |
| 휴대폰 화면 | 밝고 간결한 계정·서비스 연결과 승인 화면 |
| 첫 화면의 중심 | 오늘 방문할 업무와 다음 행동 |
| 실행 확인 | 목적지 전송과 OneNote 저장 전에 내용 확인 |
| 주행 상태 | 주차 중심 흐름에서 시작하고 플랫폼이 제한하는 UI·입력을 비활성화 |

시안은 차량의 QR·방문 업무·목적지 확인·참고 노트·음성 메모·개인 세션 종료와 휴대폰의 회사 인증·서비스 연결·노트 선택·차량 연결 승인·원격 종료를 중심으로 만든다. 화면별 색상 값, 폰트와 상세 배치는 실제 시안에서 검토한다. 현재 Figma 파일이나 로고 자산을 생성한 상태는 아니다.

## 3 기본 기술 구성

팀에 지정된 기술 경험·선호가 없고 사용자가 선정을 위임해 다음을 기본 스택으로 정했다. 선택 근거는 공식 지원과 두 명이 관리할 개발 범위다.

| 영역 | 선택 | 역할 |
| --- | --- | --- |
| 차량 앱 | Kotlin + Jetpack Compose | Pleos Connect Android UI와 SDK 연결 |
| 휴대폰 웹 | TypeScript + React + Next.js App Router | 가입·서비스 연결·노트 선택·QR 승인·세션 관리 |
| API | Next.js Route Handlers, Node.js 런타임 | 인증 처리, 개인 세션, 업무 서비스 연동 |
| 데이터 저장 | PostgreSQL | 최소 사용자 설정과 세션 상태 |
| Microsoft 인증·업무 | MSAL Node + Microsoft Graph | 허용 조직 확인, 사용자 위임 권한, 일정·메일·OneNote 연결 |
| 차량 기능 | NaviHelper, SpeechToText, 주행 규제 API | 목적지 전달, 음성 입력, 기능 제한 |

Compose는 Android의 공식 권장 UI 도구이며 Pleos의 시작 가이드는 Kotlin 프로젝트를 안내한다. 이 점을 기본 선택의 근거로 삼되, Pleos 에뮬레이터에서의 실제 UI·SDK 호환은 빌드로 확인한다. [Android Compose](https://developer.android.com/compose), [Pleos 시작 가이드](https://document.pleos.ai/en/docs/pleos-only/getting-started)

웹과 HTTP API를 같은 TypeScript 프로젝트에서 개발해 두 명이 공유할 언어·설정을 줄인다. Next.js는 Route Handlers로 서버 요청 처리를 지원한다. PostgreSQL 운영 서비스, 배포 플랫폼과 세부 버전은 별도로 정한다. [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)

Microsoft 앱 등록과 조직 정책을 확인한 뒤 서버의 MSAL Node에서 인증과 필요한 위임 권한을 검증한다. 차량에는 현재 SHIFT 세션에 필요한 접근만 부여한다. 서버용 비밀값을 브라우저나 차량 APK에 넣지 않는다. [MSAL Node 구성](https://learn.microsoft.com/en-us/entra/msal/javascript/node/initialize-confidential-client-application)

초기 기술 검증 순서는 Pleos 샘플 빌드·실행, 시험 Microsoft 계정 인증·권한 확인, 일정 조회, OneNote 조회·새 페이지 저장이다. 그 결과를 보고 SDK·빌드 도구·라이브러리 버전을 고정한다. AI 요약 제공자와 주소·좌표 검색 수단은 아직 미정이다.

## 4 GitHub 협업과 관리 주체

기능별 브랜치에서 작업하고 PR을 만든 뒤 상대방 확인 후 main에 병합한다. 예를 들어 차량 인증, 업무 정보, OneNote 연결과 문서 변경을 각각 검토할 수 있는 단위로 나눈다. 문서 수정도 같은 방식을 따른다.

PR에는 해결할 문제와 최종 동작, 실제 확인한 범위, 남은 제약을 적는다. 시연 데이터와 실제 연동을 구분하고, 실패한 검증을 통과로 표시하지 않는다. [PR 작성 양식](../.github/pull_request_template.md)을 사용한다.

| 관리 대상 | 관리 원칙 | 현재 상태 |
| --- | --- | --- |
| 배포 프로젝트·계정 | 사용자 계정을 소유자로 두고 친구에게 필요한 협업 권한 부여 | 플랫폼 선정과 실제 권한 부여 전 |
| Microsoft 앱 등록 | 사용자 소유·관리 원칙. 조직이 허용하는 앱 등록·동의 절차 확인 | 앱 등록과 권한 검증 전 |
| APK 릴리스 서명 키 | 사용자가 관리하고 필요한 빌드에 제한적으로 사용 | 키 생성·보관 위치 결정 전 |
| GitHub 변경 | 기능별 브랜치·PR과 동료 검토 후 병합 | 이번 문서 변경부터 적용 |

비밀값과 서명 키 파일은 Git에 커밋하지 않고 계정의 협업 권한과 별도로 관리한다. 담당자의 실명이나 키 값을 이 문서에 기록할 필요는 없다. 두 사람의 개발 역할·투입 시간과 팀명은 여전히 미정이다.

## 5 1차 영상 구성

PC에 차량·휴대폰 클릭형 시안을 나란히 띄워 화면 녹화한다. 계정과 선택한 노트는 준비되어 있다는 상태에서 핵심 흐름으로 진입하고, 필요한 경우 휴대폰의 연결 준비 화면을 짧게 보여준다.

| 장면 | 보여줄 행동 | 확인할 메시지 |
| --- | --- | --- |
| 차량 탑승 | 배정받은 차량의 SHIFT 시작 화면 | 기존 회사 절차로 이미 차량을 배정받은 상태 |
| 인증 | 차량 QR과 휴대폰 승인, A 환경 표시 | 현재 차량에 A의 업무 환경 연결 |
| 방문 준비 | 오늘 일정, 관련 메일 근거와 선택한 노트 | 이번 방문에 필요한 정보 확인 |
| 목적지 | 주소·후보 확인과 내비게이션 전달 | 사용자가 확인한 장소로 연결 |
| 방문 후 기록 | 음성 메모 내용 확인과 OneNote 저장 결과 | 개인 업무 도구로 기록 이어가기 |
| 세션 종료 | A의 개인 연결 종료, 공용 대기 | 해당 차량의 개인 접근 정리 |
| 다음 직원 | B 인증과 B 환경 표시 | 이전 직원의 개인 내용 접근 차단 |

관리자 등록·예약 취소·차량 반납 화면은 넣지 않는다. 1차 영상은 클릭형 시안임을 밝히고, 실제 Graph·SDK 요청이 실행된 것으로 제시하지 않는다. PT에서는 실제 연결과 결과를 시연해야 하므로 계정·권한·에뮬레이터 조건을 별도로 검증한다.

## 6 검증할 세 가지

사용자는 아래 세 가지를 모두 자체 시험하고, 가능하면 실제 외근 직원 인터뷰를 추가하기로 했다. 수치 목표는 시험 후 정한다. 현재 측정 결과와 인터뷰 완료 실적은 없다.

### 방문 준비 시간

기존 방식과 SHIFT로 같은 방문 정보를 확인해 올바른 목적지를 전달하는 시간을 비교한다. 준비 시작부터 경로 전달 결과 확인까지를 기본 구간으로 두고, 양쪽의 시작 상태와 방문 정보를 같게 맞춘다. 기존 방식은 참여자가 실제 사용하는 도구와 절차로 수행한다.

올바른 목적지 전달에 성공한 시도의 소요 시간과 실패 시도 수를 함께 기록한다. 인증·확인 조작을 포함했는지도 명시한다. 1차 클릭형 화면의 조작 시간과 실제 앱·API의 소요 시간은 별도로 기록하며, 시안 속도만으로 실제 업무 개선율을 주장하지 않는다.

### OneNote 실제 저장

내용 확인 후 저장을 요청한 시도 중, 올바른 계정의 전용 섹션에 해당 내용이 실제 저장된 시도의 비율을 확인한다. 저장 성공 응답과 OneNote 재조회 결과를 근거로 삼는다. 저장 버튼 표시만으로 성공 판정하지 않는다.

정상 저장 외에 통신 단절·권한 취소·재시도 때의 실패와 중복 여부를 기록한다. 실패 시도를 분모에서 빼지 않고, 시도 수와 성공 수를 함께 보고한다. 실제 개인정보 대신 시험 내용을 사용한다.

### A/B 정보 분리

A가 종료하거나 잠긴 뒤 B가 인증한 상태에서 A의 화면·캐시·개인 조회에 접근할 수 있는지 확인한다. 뒤로 가기, 앱 재실행, 이전 세션의 요청과 통신 단절 상태도 시험 항목으로 둔다.

확인한 시나리오 수와 이전 정보 접근이 가능했던 실패 건수를 기록한다. 시험에서 노출이 없었다는 결과와 모든 차량·다른 앱의 이력이 삭제된다는 보장은 구분한다. 이 검증은 SHIFT가 관리하는 세션과 데이터에 한정한다.

MAU·재이용률은 실제 실증 이후 지속 이용을 보는 지표로 남긴다. 초기 클릭형 시안의 평가를 대신하는 수치로 사용하지 않는다.

## 7 인터뷰와 실증

다른 회사의 공용차 이용 외근 직원·차량 운영자도 문제 확인용 인터뷰 대상이 될 수 있다. 최근 실제 이용 사례를 기준으로 다음을 확인한다.

- 방문 일정과 장소를 어느 도구에서 보고 차량으로 어떻게 옮겼는지
- 장소 변경 메일과 기존 상담 노트를 언제 확인했고 무엇이 불편했는지
- 방문 후 메모를 언제·어디에 남겼고 다시 정리해야 했는지
- 교대 때 계정·업무 정보가 남은 경험과 현재 정리 방법이 무엇인지

인터뷰한 대상의 회사 유형·업무·차량 이용 맥락과 관찰한 사례를 기록한다. 타사 사례를 현대자동차 사내 수요·도입 확정의 증거로 바꾸어 쓰지 않는다. 현대자동차 운영·IT 창구와 실증 가능 여부는 아직 확인되지 않았다.

## 8 남은 결정과 다음 산출물

다음 산출물은 핵심 화면 시안, 클릭형 프로토타입과 PC 화면 녹화 영상이다. 그 뒤 실제 Pleos 앱·Microsoft 연동을 구현한다. 이번 계획 확정과 실제 제작·설정 완료를 구분한다.

팀명, 개발 역할·시간, 화면의 상세 배치, 배포·DB 운영 서비스, 비밀값 보관 위치, AI 요약과 좌표 검색, 비활동 잠금 시간·판정 기준, 기록 보관 기간과 실증 규모는 후속 결정으로 남긴다.
